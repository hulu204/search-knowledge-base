# 1. 背景介绍

在小米商城推荐系统中，不同时期相似用户人群的兴趣偏好以及商品之间的相关性会有差异，特别是在大促与非大促期间，因此，这要求推荐系统线上部署的模型需要不断捕捉新的数据模式，保证一定的实时性。线上模型的更新方式一般包括批量更新（Batch）和增量更新（Incremental）：批量更新基于一个固定时间长度的窗口内的数据每次从头开始训练，更新一天的数据，时间窗口就向前滑动一天；而增量更新基于新数据，是在已经存在的模型上继续学习。可以看出，批量更新每次训练的样本较大，需要的训练时间较长，并且模型只能学习到滑动时间窗口内的数据模式。目前，小米商城的排序模型均采用增量更新模式。

![](https://mmbiz.qpic.cn/mmbiz_png/7IvGcxnNcwOqHQEnZ3s5YicokRxUe2UEjB6j8zPxSwInQM0A01fCZhP8Xg2iaqicXDcRmeOFWCmuLaId5sesTbWUQ/640?wx_fmt=png)

图1：模型的更新方式 Batch Mode vs Incremental Mode

增量更新模式训练的模型得益于长期的数据积累，其效果往往要比初期部署时好很多，举例来说，如下图，商城使用Embedding+MLP范式的一版点击率预估模型，其AUC虽然在短期内是有波动的，但在经过9个多月的增量更新后，线上模型AUC提升大约4个百分点，这个现象说明数据积累的必要性，也说明在模型迭代过程中一个好的warm-start方法的重要性。

![](https://mmbiz.qpic.cn/mmbiz_png/7IvGcxnNcwOqHQEnZ3s5YicokRxUe2UEjkN7amRG0vlsQkxgMyesUHgyaMUZ8faQtLcQZoS6mkkEcjaUBRFqTZw/640?wx_fmt=png)

在做模型迭代时，我们通常先做离线评估，再逐步开启线上流量。对推荐场景来说，更希望关注GAUC，即每一个用户是独立的排序，但在衡量指标时又不得不选择AUC是因为，GAUC相对波动较大。在多次测算中，发现预测样本在千万量级时，AUC误差大体在0.001以下，GAUC误差大体在0.01左右，上亿样本时GAUC的波动依然有0.005左右，因此GAUC虽然是个好指标但波动太大，很难在现实场景中得到应用，最终在真实业务中我们主要依据AUC判断模型的效果。

在模型迭代过程中，之前常规的的做法，我们会先使用cold-start方式做新旧模型的线下公平对比，即base模型和新模型参数全部随机初始化，选择一个相同的时间窗口（如7天）做批量训练，如果AUC提升在0.004以上，我们就认为是有效提升，然后就将新模型小流量上线。

但这么做经常会碰到一个问题：因为线上的base模型可能已经增量更新跑了很久，相当于是用很长时间窗口（比如几个月）的样本训练过的，而刚上线的新模型只用了7天训练数据，很难一开始就打败base模型，甚至差很多，需要相当长的时间才能追平或超越，严重影响了算法迭代效率，甚至有时候会误导我们的判断，以为是新模型线上线下效果不一致。举个例子，我们有一版CTR新模型，线下公平对比AUC提升了0.01，但和线上的base模型比低0.02，新模型上线经过两个多月的增量更新后，这个gap仍然有0.005，而且gap缩小的速度越来越慢，想要完全追上线上版本，可能需半年到一年的数据。

因此，如何能够让新模型在上线伊始尽量缩短和base模型的差距，就成为一个需要迫切解决的问题。

# 2. 模型热启方法

首先很直观想到的是，加大新模型上线前的训练样本时间窗口，但这种方法一方面很不经济，需要大量的算力和存储，一方面有时候是不可能完成的任务，比如某个新特征依赖的埋点是最近才刚刚加上的，历史上就没有。

其次想到的就是能不能利用base模型的信息，通常新模型都是在base模型基础上做优化更新，比如增删特征、修改模型结构，因此新旧模型有着千丝万缕的联系。这种在新模型初始化阶段复用旧模型信息的方法我们称之为warm-start，具体方法经历了下面几种演化。

## 2.1 复用Embedding

Embedding+MLP范式的模型中，Embedding层的参数规模占比非常高，旧模型中公共原始特征的embedding可以利用起来，作为新模型embedding的初始化参数，其他参数随机初始化。通常来说，新加的特征毕竟是少量，大部分还是原来的特征，因此复用率还是相当可观的。但是实验结果并不乐观，相比cold-start有提升，但跟线上base模型差距还是很大。

## 2.2 复用Embedding+MLP

我们的算法迭代工作大部分情况下，都是只增不减，比如增加新特征，增加新的网络结构。这种情况下，不只embedding可以复用，MLP的参数也可以复用。新增的参数采用随机初始化。这次的效果异常好，已经略微超过了线上base模型。

# 3. 具体实现

## 3.1 复用Embedding

离线训练时保存了模型的checkpoint模式，为了方便线上部署，离线训练完的模型还会导出saved\_model模式。为了加快线上推理效率，在导出模型时，把整个图分裂成两部分：

* 稀疏特征转化层的embedding单独导出成文件id\_map；
* embedding聚合层（例如attention）和深度层单独导出成tf-serving模型（pb格式）；

在复用已有模型的embedding时，可以通过解析id\_map文件来初始化新模型的Hashtable实现。

## 3.2 复用网络结构

增量更新时，我们可以从checkpoint里恢复模型，但一旦模型结构更改，则很难直接从checkpoint里恢复，因此采用移花接木方式：从checkpoint里恢复模型并对网络结构按照新模型进行更改，并重新存储，具体的在代码中采用MonitoredTrainingSession来管理Session，一个完整的MonitoredTrainingSession在创建时间内可做的事情（按顺序）：

* 为每个hook调用hook.begin()
* 调用scaffold.finalize()完成graph
* 创建session
* 为模型参数做初始化 ，通过Scaffold
* 如果存在checkpoint则根据checkpoint restore参数
* 发布runners队列
* 调用hook.after\_create\_session()函数

MonitoredTrainingSession在从已有checkpoint恢复训练、完成变量的初始化的同时，也结束了当前的计算图（使之成为只读），因此，在对图做修改之前首先需要“unfinalize”计算图：

```
sess.graph._unsafe_unfinalize()
```

**case1：新增、删除特征**

![](https://mmbiz.qpic.cn/mmbiz_png/7IvGcxnNcwOqHQEnZ3s5YicokRxUe2UEjqlLCMbwvOaPJUxrDwzQr5CwCtWzXiaOE9zj2EPNqw7kTlG2yVia2wY7w/640?wx_fmt=png)

新增特征的第一个要点是要初始化新增特征的Hashtable，并补充到全局表self.\_hash\_tables：

```
params = []  
  
for i in range(self._num_shards):  
  
    table = tf.contrib.lookup.MutableHashTable(  
  
        key_dtype=tf.int64,  
  
        value_dtype=tf.float32,  
  
        default_value=[-0.01] * embedding_size,  
  
        hash_table_segments=self._config.hash_table_segments,  
  
        tensor_cache_size=self._config.hash_table_cache_size,  
  
        feature_clean_num=self._config.feature_cleaning_num,  
  
        initializer=initializer,  
  
        name=self.hash_table_key_pattern(group_idx, i))  
  
    params.append(table)  
  
self._hash_tables.extend(params)
```

第二个要点是拿到新增或删除特征的位置：为了拿到需要修改的网络层，我们在模型结构基类ICustomStructure中定义了一个字典\_scope\_fc\_layers来存储，当然如果能取到变量名，通过get\_tensor\_by\_name方法应该也是可以的。

第三个点是修改相应的权重变量：原始特征对应的权重采用之前训练好的参数，新特征则随机初始化，然后依序拼接。
