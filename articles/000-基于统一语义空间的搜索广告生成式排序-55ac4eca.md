**背景**

百度商业广告推荐系统中，长期依赖大规模离散ID建模范式，虽然该范式经过多年工程积累取得了实际效果，但其本质仍是一种****记忆驱动的建模机制****，在语义表达与结构泛化能力上存在显著天花板：

* 共现稀疏限制泛化：在万亿级ID空间中，长尾ID缺乏足够共现支撑，模型难以有效建模兴趣迁移与行为组合；
* 语义割裂阻碍意图理解：语义相近的实体（如“新能源汽车”与“电动汽车”）在随机哈希编码下完全无关，难以聚合学习，限制用户意图建模；
* ID漂移破坏连续性：随着系统运行中 ID 持续新增与下线，Embedding 空间不稳定，影响模型一致性与用户长期兴趣追踪。

上述问题在搜索等强意图场景中尤为突出，使传统的 ID 驱动排序模型的优化逐步接近其理论极限。大语言模型（LLM）已在自然语言建模中展现出强大的语义理解与生成能力，其成功范式为推荐系统提供了明确的进化方向。在《GRAB-百度推荐广告生成式排序模型技术实践》一文中，我们介绍了在推荐场景落地的生成式推荐排序模型，但其序列化表征仍依赖离散ID。

我们认为推荐排序系统应逐步从离散ID驱动的记忆范式，演进为基于语义token与生成机制的类语言模型结构。用统一、可组合的语义token替代离散ID，基于生成式结构，在闭集token空间中建模行为路径、意图跳跃和长程依赖，从而真正释放大模型的语义理解能力。

本文聚焦于统一语义空间构建与生成式排序建模的技术路径，系统性阐述我们相关的探索与实践。

**技术演进**

从建模能力出发，直接以LLM替代传统排序架构能够最大程度复用大模型能力，但在当前工程条件下，超长序列与极高推理成本使其难以在落地。因此我们选择一条渐进式、兼顾性能与可落地性的技术路径：

阶段一：静态语义增强。将LLM作为语义特征提取器，增强Query与广告的语义一致性与长尾表达；

阶段二：静态语义表征到语义ID。对LLM语义向量进行量化，构建闭集语义token空间，并以多粒度语义级联编码（MSC）平衡泛化与记忆；

阶段三：****统一语义空间下的生成式排序****。在统一token空间内进行序列建模与偏好生成，显式建模迁移、跳跃与层级组合。

## 2.1 静态语义增强

在强意图检索与广告场景中，语义理解能力对模型至关重要，为此，我们首先引入基于 LLM 的语义编码作为增强信号，以提升模型对用户意图理解能力。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxb1tELFPDkAK4hC30M3pWSFDugCYiahFEiateMbMGE0NOnIMJuXJfz52jQ/640?wx_fmt=png&from=appmsg)

****语义对齐：****LLM基于大语料预训练，能很好地提取文本的语义表征，但缺少商业语料的训练。因此我们使用检索日志点击等共现行为构造query2query/item2item语义对，通过对比学习进行微调，使开源语义模型适配商业检索语境。

****语义表征：****我们通过LLM编码检索词、广告标题、广告描述等字段的语义表征；

****跨模态融合：****由于离散ID embedding与语义表征 存在空间、尺度和语义对齐不一致的问题，直接拼接往往难以取得理想融合效果。为此，我们设计了一种****跨模态融合网络（CFN）****，借助语义表征动态生成融合网络参数，以引导ID embedding进行语义对齐：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbzy85LVewh1eREnkNPAiabmmdY5xssN87vu3fGI6YgDlpVNUC2rs80Bg/640?wx_fmt=png&from=appmsg)

其中CFN的参数由一个轻量网络根据语义表征动态生成。

本阶段方案引入了更具泛化能力的语义表示，有效提升了模型在冷启动、稀疏场景下的效果。

## 2.2 从静态语义表征到语义ID建模

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbrTIIt5CxljMkNYTxBVtqoyNmPfJrjdMI5Cjia61xpyrDayicZq1wyC8A/640?wx_fmt=png&from=appmsg)

静态语义表征增强在⼀定程度上提升了模型的实体语义⼀致性与⻓尾泛化能⼒，但该⽅式仍受限于语义表示的静态性，⽆法应对⽤户偏好的实时演化，因此我们进⼀步将其量化为语义ID。

我们采用RQ-KMeans方案对语义表征进行量化，并设计了一种由粗到细的多粒度语义级联编码MSC（Multi-scale Semantic Cascade），以平衡泛化与记忆：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbWWcuHRmnkMlsJgFc2QXo9WO16MnBwvlU2BnicO4ztklYaVTpiczutgfw/640?wx_fmt=png&from=appmsg)

其中，Sk = (C1, ..., Ck) 表示第 k层级联子结构，包含前 k 层语义粒度。

除基础特征外，我们同样使用MSC策略对用户行为序列进行重构。设用户历史行为序列为S = X1, X2, ..., XT则其语义ID序列重构形式为：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbsqMFJvicDMoy3t4Hb6GOHhEywF7WuEGm8icDtr9hOEA4jT50Bliaxs4icQ/640?wx_fmt=png&from=appmsg)

即每个历史行为 Xi 被展开为3个token：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxb1TGyCvOiarLj8dGNqzGyYpOp7JmnLsshZHvJ7cXz9v9m6NPTMKickCYQ/640?wx_fmt=png&from=appmsg)

从而构成一个递进层次化的长序列。

与静态语义embedding相比，语义ID不仅保留了语义泛化能力，还能够在流式更新中持续学习用户偏好的动态变化，在很大程度上克服了传统离散ID表示的稀疏性、语义隔离与表示漂移等核心瓶颈，使模型的稳健性与表达能力得到进一步提升。我们已在系统中逐步以语义ID替代传统离散ID体系，以构建一个统一的闭集输入结构。

## 2.3 基于统一语义空间生成式排序

语义ID让我们得以将排序模型的的输入空间迁移至统一语义token空间，为进一步迈向类语言模型范式奠定了基础。

然而语义ID建模最细粒度的 [C1,C2,C3]，仍属于笛卡尔组合空间，呈现出显著的高维稀疏性，难以支持稳定的语义共现学习。为此我们进一步将 [C1,C2,C3] 拆解为 C1,C2,C3，使语义输入空间由乘法式的笛卡尔积结构 N1xN2xN3 转化为加法式的并集空间 N1+N2+N3，从而将推荐系统的输入重构为类语言模型中常见的闭集token序列。

与此同时，我们也充分考虑到工业实践中的系统演化现实：传统的离散ID建模体系经过多年演进，难以在短期内彻底移除。为此，我们设计了一种****渐进式替换机制，****在前期以语义ID与开集ID（主要是广告ID）融合的方式维持连续性，并在训练中显式强化语义ID对原有ID的重构能力；随后逐步以语义ID替换开集ID，实现平滑过渡与无损升级。

### 2.3.1 序列构造与输入组织

****序列工程****：实际业务中搜索/信息流、商业/自然结果各自使用不同的 ID 体系，长期难以统一建模。通过引入语义ID，我们得以将这些跨域行为统一映射到共享的语义空间中，实现跨场域行为的联合建模。

****序列组织****：采用更契合搜索场景的 PV 级组织方式，以每次检索 Query 为锚点，在其后拼接广告行为，形成层次化历史序列：

### 2.3.2 模型结构

****Encoder–Decoder****：搜索历史跳跃性强、因果依赖弱，点击之间常跨主题/跨品类，严格自回归的历史依赖往往不可取，我们采用 Encoder–Decoder 结构：

* Encoder 仅接收请求级信息（历史 + 当前 Query），因此其输出可在同一请求内一次前向、跨候选复用；

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbqCibZ5G6ebic4POhXxhfOiaxicr17OTv0vYuqGwDgIEvjj0rBmQibuZmodg/640?wx_fmt=png&from=appmsg)

* Decoder 基于目标表示进行条件生成与打分，作为辅助任务增强模型效果；

****Cross-attention****：考虑到工业系统中已有的大量ID体系短期内难以彻底替换，我们设计了渐进式替代策略，候选token由语义ID与残留的离散ID融合，以实现对ID特征的平滑兼容与渐进替代

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbUFg2Af8tzNHDm4oZGHVvRNj7PYthUkObLnia2c7rqIuuNBo4ROiaPpLQ/640?wx_fmt=png&from=appmsg)

如图所示，参考 Q-Former，我们为每个候选构造m个候选查询与历史行为做跨注意力交互，聚焦历史的不同语义子空间。

****训练目标****：排序主目标采用交叉熵 ，辅助生成目标对语义ID各层级做自回归预测。

### 2.3.3 长序列建模

在语义ID引入后，每个用户行为由多个语义token构成（如C1,C2,C3），行为序列也因此显著膨胀为K倍，显著增加了实际参与计算的序列长度与计算成本。我们设计了两类互补的结构优化策略，分别从序列压缩与结构并行两个方向提升长序列建模能力。

Token Merger：以压缩换容量。对每个行为的多层语义 token 进行压缩融合，以提升单位长度内的行为覆盖数。具体而言，将每个行为的 C1,C2,C3 token输入一个轻量Transformer结构，得到融合后的压缩表示：

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbv9UstW4G6Cor59CfP0iajyGxqYxnIGFfbseEk7ecnPO99PEiav7vUJbQ/640?wx_fmt=png&from=appmsg)

此方案允许我们以压缩换容量，将每个行为从K个token压缩为1个，从而引入K倍以上的行为序列，其序列增广效应可大幅提升模型效果。

****多通道建模****：以拆分换深度。在某些用户行为极长或跨域行为差异明显的场景中，单通道序列即使经过压缩，也无法容纳所有行为序列。为此，我们使用多通道建模机制，即按照场域对用户历史行为进行拆分，并在多个独立通道上并行建模。

## 3.1 分布式部署的时延瓶颈

传统流式系统的设计理念长期侧重于****分布式部署****，以追求低成本、高可用和弹性扩展。然而，传统的分布式流式系统中（如基于 Flink 的架构）固有的****跨节点通信、数据同步与一致性维护开销****，在高频数据链路下逐渐成为制约时效性的主要瓶颈。

* ****跨节点通信延迟****：上游算子与下游算子之间需通过网络传输数据，即使在同一集群内部，也存在 RPC 调度与网络堆栈延迟。
* ****数据序列化与反序列化开销****：节点间传输的数据需要经过频繁的序列化处理，尤其在高吞吐场景下成为主要性能瓶颈。
* ****状态同步与快照开销****：在商业场景下大多需要保证数据的不重不丢，Flink 为实现 exactly-once 语义，需要周期性对算子状态进行 checkpoint 与 barrier 对齐，这在大规模任务中会造成明显的系统抖动与滞后。
* ****调度与反压机制引入的额外延迟****：当某个节点处理能力不足时，Flink 会触发反压机制，造成整个流图处理速率下降，影响端到端时延。

## 3.2 向大单体架构演进的挑战

随着硬件技术的持续演进，高性能、大内存的单机节点已具备承载过去分布式系统典型负载的能力。在此背景下，我们重新审视了系统架构取舍，提出以****大单体部署（Large Monolithic Deployment）****为方向的系统升级方案。通过整合数据接入、处理与发布模块，显著减少跨节点通信与序列化开销，从根本上提升数据流的实时性。

然而从分布式部署迁移到大单体部署并非简单的物理整合，而是一次系统性的架构重构。分布式架构所依赖的高可用、弹性扩展、状态一致性与容错机制，在单体化后都需要以不同的方式重新实现或强化，主要难点有

* ****高可用保障困难****：单机部署天然失去分布式多节点冗余能力，一旦主进程故障，可能影响整体服务可用性。
* ****扩展性受限****：单体模式下水平扩展能力下降，如何应对流量高峰与业务增长成为关键问题。
* ****状态一致性与Exactly-once语义实现复杂****：分布式环境依赖的快照与事务协议不再适用，需要重新设计可靠的本地一致性机制。
* ****状态管理与恢复时延：****大量有状态计算在单机集中管理时，状态体积增大导致快照、恢复和迁移成本显著提升。

## 3.3 渐进式优化方案

为在工程上平衡****系统时效性提升****与****架构稳定性演进****之间的关系，我们采取了分阶段、渐进式的迁移路径。总体策略是——****先融合、再单体化、逐步演进、确保稳定****。在实施过程中，我们主要从以下几个方向展开优化与演进：

* ****混合架构（Hybrid Deployment）：****首先，通过整合原有分布式部署中的核心数据通路模块，在保留部分分布式容错能力的同时，显著降低跨节点通信与序列化开销，为后续的大单体部署奠定基础。下图是我们在流式反作弊系统中的工程实践，通过整合多个策略处理模块，减少了算子之间 RPC 交互，以及中间结果读写文件系统交互所引入的开销，该阶段的耗时由秒~分钟级别降低至毫秒~秒的粒度。
* ****分片化单体设计：****用业务或 key 范围把用户分片到多台“单体节点”，由上游路由层做分片路由。
* ****外部化持久化与快照机制：****将关键的状态信息与中间结果托管至外部高可靠存储系统，结合周期性快照实现崩溃恢复，在保持性能的同时，仍能提供接近分布式架构的可靠性与一致性保障。
* ****幂等与去重机制：****通过为消息与事件设计全局唯一标识，结合去重索引与幂等逻辑，确保在单机重启、重复推送或任务恢复场景下，系统能够保持 exactly-once 语义。

通过上述优化路径，我们逐步完成了从分布式到大单体的架构演进，在****时延降低、吞吐稳定性提升、系统可维护性****等方面均取得显著收益，为模型的实时训练与推理提供了高效、稳定的数据流支撑。

语义ID需要使用LLM对物料文本进行编码，传统方案采用离线批量计算配合天级别的KV表更新实现，但是无法完全覆盖实时的请求。为了覆盖长尾流量，提升策略效果，LLM需要做到在线实时计算。

## 4.1 系统性能挑战

* ****时延瓶颈：****Query侧和Ad侧在链路中只有不足十毫秒级空间，难以实时计算。
* ****吞吐瓶颈：****Query侧高峰期请求QPS高达数万，而Ad侧更高达百万，实时计算资源面临巨大挑战。

## 4.2 推理架构

通过使用请求预计算、近线推理架构、PULL调度、动态batch，使Query侧和Ad侧在线化计算在合理的资源预算下由不可能变为可能。

* ****Query侧——请求预计算：****Query侧严苛的latency空间让在线计算难以实现，通过对业务流程的梳理，我们发现在推理流程早期我们就可以获取到Query信息，因此我们对链路进行改造，在系统更早期阶段发起请求，在真正计算时通过直接查询cache的方式为Query请求争取到了额外的latency空间，实现了请求全量覆盖。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbc0NXZ9uwCkF2RQco0Sop64NoFAUN6icKib4UhuKWYSFcXgCP5MDjrxDw/640?wx_fmt=png&from=appmsg)

* ****Ad侧——请求近线推理架构：****在线推理系统难以满足Ad侧极致latency限制。

* 我们观察到：

1. 在线通路无法实现推理：
2. 飞火在线推理服务流程主要包括cache查询，切词，推理。其中推理耗时比重最大且远无法满足latency限制。
3. **无法使用预计算：**Ad需要经过召回，改写等一系列流程，请求LLM的位置已经无法再提前。
4. 请求存在时间局部性：通过对请求的分析，相同Ad在一定时间段内会存在大量重复请求，使用cache能够有效降低系统负载

* 我们提出在线通路实时返回cache结果+近线通路延迟更新cache的机制，利用Ad请求的时间局部性特征，仅使用少量GPU实现了Ad请求90%+的实时覆盖率。

1. ****【在线通路】****由上游服务请求，只负责cache查询，以及保存未命中cache的请求日志
2. 【****近线通路****】由日志处理服务搜集在线通路日志，上传至消息队列。同时由流式计算服务订阅消息队列中的请求并组装batch，随后请求飞火模块执行LLM推理，并更新cache供在线通路使用。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/Te8D0eD8ugydHKb13ImpuE95B3lTmTxbHzSicnnvYnicKPKCyyqkJqvlAlwqicIOGWqs9JjFzTaicDKNib9NHKibo3Qw/640?wx_fmt=png&from=appmsg)

* ****其他优化：****对于Query侧和Ad侧，我们在调度上使用PULL调度+动态batch，优化负载均衡并且提升吞吐。

+ ****PULL调度：****在超大qps，且模型推理耗时受输入长度分布波动较大时，系统将面临时间和实例维度的请求负载不均问题。通过引入PULL调度，LLM推理任务被推入一个全局优先队列，服务每个实例自行拉取负载，最终解决负载不均问题，让系统吞吐与实例数量保持线性关系，系统预算保持可控。
+ ****动态batch：****LLM推理batch size由上述PULL调度全局队列负载情况自动调节，在保证系统吞吐的情况下最小化batch计算带来的调度开销。
